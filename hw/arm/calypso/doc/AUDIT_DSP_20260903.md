> Perimetre : `hw/arm/calypso/` de **qosmo-dsp** (identique a `qemu-src` — `diff -rq`
> sur le repertoire = 0 ecart). Objectif : etablir ce que le DSP emule fait

## 2. Ce que le DSP fait, etage par etage

| etage | etat | preuve |
|---|---|---|
| execution mask-ROM | OK | 4 PROM reelles (`tools/calypso_dsp.PROM0..3.bin`), ~500 k insn/s, `unimpl_count` nul |
| entree demod alimentee | OK | `data[0x4c00]` lu a `PC=0x9fb5`, valeurs reelles variables |
| **FB / FCCH** | **OK — acquis par le vrai DSP** | `d_fb_det[0x08f8] 0->1` **x437**, ecrit par la ROM a `PC=0x79e4` ; `FB1: TOA=39, Power=-52dBm` |
| **SB / SCH** | **MUR** | `a_sch[0]=0x8100` (`B_BLUD\|B_SCH_CRC`) -> `prim_fbsb.c:181` abandonne ; `a_sch[3]=0xf8d8` **constant sur 21/21** pour 10 bursts distincts |
| a_pm / rxlev | modelise, pas mesure | le DSP ecrit 0 ; substitue par le modele RSSI (MAV du DL -> calib trf6151) |
| DMA on-chip | non modelisee | `d_error_status = 8 (DSP_ERR_DMA_PROG)` permanent, 404 occurrences |
| camp / LU / SMS / voix en natif | KO | consequence du mur SCH |

**Le fait qui compte** : un decodeur dont la sortie ne depend pas de l'entree ne
decode pas. `a_sch[3]` constant sur 21 ecritures pour 10 entrees distinctes est le
seul symptome qui merite du temps aujourd'hui.

## 3. Les verrous, par ordre de rendement

### V1 — L'IT trame partait sur le mauvais vecteur *(CORRIGE le 2026-09-03)*

Le defaut le plus structurel, entierement caracterise dans le code lui-meme :

- `calypso_c54x.h` portait deja la **bonne** table (CAL207 §15.1, `vec = Location/4`) :
  l'IT trame TPU est **INT8n = bit 12 / vec 28**. Recoupee par la mesure — l'IMR du
  ROM (`0x52ed`) n'a de sens que sous cette table.
- Le meme header marquait `C54X_INT_FRAME_VEC 19 / BIT 3` **LEGACY** : c'est TINT, le
  timer du DSP, dont le ROM n'a qu'un stub `RETE`.
- **Mais `calypso_trx.c` emettait toujours `c54x_interrupt_ex(dsp, 19, 3)`.**
- La correction n'existait qu'en **remap a l'execution** dans `c54x_interrupt_ex()`,
  gate par `CALYPSO_DSP_FRAME_VEC28` **ou** `CALYPSO_FRAME_IT_NATIVE`, **defaut 0**.
- Et le test d'armement lisait le **bit 12** quand ce gate etait pose, puis emettait
  sur 19/3 : **le test et l'emission ne parlaient pas du meme vecteur.**

Applique : emission sur `C54X_IT_TPU_FRAME_VEC/BIT` a la source dans `calypso_trx.c`
et `calypso_bsp.c` ; suppression du remap, des deux gates, du `frame_force`, du sas
`CALYPSO_IT_TABLE_DOC` et des defines legacy. Le mode shunt emettait deja
`c54x_interrupt_ex(dsp, 28, 12)` en dur : la cible etait **deja exercee**.

### V2 — Le decodeur SCH : sortie independante de l'entree *(OUVERT)*

Le mur actuel. Trois hypotheses, par cout croissant :

1. **Le burst SB n'atteint pas le tampon lu par la routine SB.** Le meme piege a deja
   coute cher cote FB : `CALYPSO_BSP_DARAM_ADDR` valait `0x4c00` = **bloc de controle**
   du DSP (le burst ecrasait le pointeur `cala` en `0x4c0c`), corrige en `0x2a00` le
   2026-08-22. A verifier **avant tout** — c'est une mesure, pas une conjecture.
2. **Opcodes du chemin Viterbi / FIRE.** `RAPPORT_OPCODES.md` liste ~40 findings dont
   ~15 de gravite 1, et **deux plages entieres n'ont jamais eu de passe de
   refutation : `0x60-0x8F` et `0xC0-0xFF`**. Or `0x60-0x67` (`mpy`/`mac`) et
   `0x78-0x7D` (`macp`/`macd`) sont decodes **en 1 mot la ou binutils en donne 2** :
   dans un decodeur convolutif, un decalage de longueur d'instruction produit
   exactement le symptome observe — une sortie figee.
3. Le `0xf8d8` constant est peut-etre une **valeur d'initialisation** jamais ecrasee,
   auquel cas la routine de decodage n'est pas atteinte du tout.

Ordre recommande : **hypothese 1, puis 2**. V1 etant leve, l'etage est desormais
atteint sans reroute — la mesure devient interpretable.

### V3 — Le vecteur de livraison RX est faux *(OUVERT, decision a prendre)*

Trouve pendant l'audit, documente dans `calypso_bsp.c` mais jamais tranche : les
bursts RX sont annonces au DSP sur **vec21** (XINT = SPI **transmit**) et **vec19**
(TINT = timer). Mesure du 03/08 : `vec21=24644 vec19=24857 vec30=0`, soit ~49 000
bursts annonces sur deux vecteurs qui n'ont aucun rapport avec la radio et dont le
ROM a des stubs `RETE`. **Le correlateur n'est donc jamais prevenu qu'un burst est
arrive** — c'est un candidat serieux pour V2/hypothese 3.

CAL000 §3.7.1 autorise deux vecteurs pour le RIF, selon le mode, **tous deux
demasques dans l'IMR relevee (0x52ef) et emis par personne** :

| vecteur | bit | ligne | mode |
|---|---|---|---|
| 16 | 0 | INT0n « RIF receive » | XIO mot-a-mot |
| 30 | 14 | INT10n « DMA interrupt » | buffered, canal dedie RIF-RX |

Se departagent en **un run chacun** : `CALYPSO_BSP_RX_VEC=16`, puis `=30`.

### V4 — `a_pm` n'est mesure nulle part *(TRANCHE le 2026-09-03)*

Dans tous les modes, natif compris, `a_pm` etait substitue, par l'un de deux
substituts : `apm_for_rf(-60)`, une **constante decretee**, ou le **modele RSSI** qui
derive `20*log10(MAV/MAV_REF)+RF_REF` de la magnitude reelle du DL. Le second est
legitime — il modelise un registre HW de puissance cote ABB absent du modele ADC, et
son ancrage est une calibration de frontend, pas une valeur choisie. Le premier est
une bequille. Le premier est supprime, le second conserve et rapatrie dans le BSP.

## 4. Le piege de la suppression du shunt

**Quatre chemins dont le mode natif depend vivaient a l'interieur de
`calypso_dsp_shunt.c`.** Supprimer le fichier sans les porter tuait le natif.

La cause est un nom trompeur : `calypso_dsp_shunt_active()` ne voulait pas dire « le
shunt est actif » mais « l'infrastructure shunt est armee », et elle valait **VRAI
des que `CALYPSO_DSP=c54x`** — donc **en mode natif aussi**, en mode dit « assist ».

| ce qui vivait dans le shunt | qui s'en sert en natif | traitement |
|---|---|---|
| `fb_stream_next()` | `c54x.c` — **FB-STREAM, l'entree du correlateur natif** (`CALYPSO_FB_STREAM=1` dans `calypso_native.env`) | porte -> `calypso_bsp.c` |
| `get_task_md()` | `bsp.c` x3, `c54x.c` — gate les wires BRINT0 sur la mission FB/SB | porte -> `c54x_task_md()` |
| `rssi_apm()` + MAV | `c54x.c` — le modele a_pm (V4) | porte -> `calypso_bsp_rssi_apm()` |
| `early_booted` / `set_c54x` | `trx.c`, `mb.c` — **ne pas re-reset le c54x**, pour preserver la commande bootloader de l'ARM | porte -> `c54x_early_boot()` |

## 5. Dette de configuration

279 variables d'environnement dans `hw/arm/calypso/` seul ; `VARIABLES_ENVIRONNEMENT.md`
fait 215 Ko. `shunt.env` classait ses 58 variables en 7 legitimes / 17 sondes /
**34 bequilles**, et notait que « `=0` ne coupe pas tout : quatre idiomes coexistent » —
certaines testent la **presence** de la variable, donc seul `unset` les desactive.

Consequence mesuree : `CALYPSO_TRF_RXLEV=0` **ne coupait pas** sous `SHUNT_LEGIT=1`,
l'idiome `(d=='1') || (l=='1')` laissant le parapluie ecraser un 0 explicite.

`calypso_gate()` est la bonne primitive (defaut parametrable, le `0` explicite gagne).
Elle n'est pas generalisee : **tout site encore en `getenv() && *e=='1'` est un piege
de mesure.** Chantier mecanique a fort rendement.

## 6. Ce qui a ete fait le 2026-09-03

`-6 976 / +647` lignes, build propre (`ninja qemu-system-arm`, 0 erreur 0 warning).

- **V1** applique (§3).
- Les **4 chemins du §4** portes hors du shunt.
- **Shunt supprime** : `calypso_dsp_shunt.c/.h`, `calypso_dsp_helper.c`,
  `calypso_dsp_internal.h`, et le modele L1 HLE `calypso_layer1.c/.h` — ce dernier
  etait de toute facon **inexecutable** (sa garde exigeait `l1_c_active() &&
  !shunt_active()`, or `l1_c_active()` rendait `shunt_active()` vrai).
- Bequilles retirees au passage : les **3 gates BSP** de `TODO.md` §P2 (dont celui
  qui ne se levait qu'avec `TPU_RX_WIRE`, si bien que `BSP_DARAM_FORCE=1` ouvrait
  deux verrous sur trois et que rien n'arrivait au DSP) · le gate shunt sur la **DMA
  de tache ARM -> DARAM 0x0586**, qui faisait entrer le correlateur **sans mission** ·
  `FORCE_TOA` · `FORCE_NB` · `FORCE_FBSB` · `FORCE_AGCH` · la force `d_fb_det=1` ·
  le `val=24` ALLC · le wire `d[0x3f92]` · les sondes `record_rach` et
  `TCH_DL_PROBE` · `l1ctl_inject_dl_si` · FN-FIX.
- **Sas `CALYPSO_IT_TABLE_DOC` vide** : TINT est desormais emise sur vec19/bit3 sans
  condition. ⚠️ **Changement de comportement non mesure** — l'IMR relevee a le bit 3
  demasque et le bit 4 masque, donc l'IT timer, jusqu'ici silencieusement jetee, est
  maintenant reellement dispatchee sur un stub `RETE`. Effet attendu benin, mais
  « attendu » n'est pas « mesure » : a verifier au premier run sous charge.
